1. Product Overview
Product Name
Mini D-Mart — Grocery Store Application
Product Vision
Mini D-Mart is a full-stack grocery shopping platform that enables customers to browse and purchase grocery products, manage their cart, place orders, choose between scheduled store pickup and home delivery, and request returns or exchanges.
The system also provides dedicated dashboards for staff and administrators to manage orders, inventory, pickup schedules, delivery operations, products, users, and return/exchange requests.
The application will be designed as a real-world product rather than a basic CRUD application.
2. Problem Statement
Traditional grocery applications require coordination between customers, inventory, order preparation, pickup scheduling, delivery, and post-purchase support.
The system must solve the following problems:
Customers need an easy way to browse and purchase products.
Product stock must remain accurate during checkout.
Store pickup must support scheduling and capacity limits.
Staff must efficiently manage incoming orders.
Administrators need control over products, inventory, users, and operations.
Returns and exchanges require eligibility checks and approval workflows.
Unauthorized users must not access restricted functionality.
3. Product Goals
Primary Goals
Build a complete grocery shopping workflow.
Implement secure authentication and authorization.

Provide product, inventory, cart, and order management.

Decision — Low stock threshold: The threshold was previously undefined. Decision: implement it as a global, admin-configurable setting (e.g. a single "low_stock_threshold" value, default 5) rather than a per-product field, to keep MVP scope small. A per-product override field may be added later (see Future Enhancements) if time allows; note this choice in the technical design doc so it is not re-litigated mid-build.

13. Exchange Management
Customers may request an exchange.

Exchange Rule
If the replacement product is unavailable: exchange cannot be approved until stock is available.
Decision — Exchange ↔ order status interaction: Not previously specified. Decision: an approved exchange does NOT mutate the original order's top-level status (it stays COMPLETED/DELIVERED). Instead, the exchange is tracked purely via the ReturnExchangeRequest record: status moves REQUESTED → APPROVED → COMPLETED once the replacement has shipped/been handed over, and a note (metadata) links back to the original OrderItem. No new Order row is created for the replacement item in MVP scope. This keeps order history accurate while avoiding a second checkout/payment flow. Document this explicitly in the technical design so frontend and backend agree on it.

New — Security Testing (required, previously missing): The assessment brief calls out Security Testing as its own weighted category. This was not covered by the original testing plan and is added as a mandatory checklist below.
Security Testing (New)
In addition to functional tests, the following security-focused checks must be performed and their results recorded (see Section 22, Security Review):
Input sanitization / injection checks — attempt SQL injection and script injection payloads against key endpoints (login, search, product filters) and confirm the ORM/serializer layer rejects or safely escapes them.
Broken access control probing — as an authenticated Customer, attempt to access another customer's order, cart, or profile by directly changing IDs in the URL/body (IDOR-style tests).
Privilege escalation attempts — as Staff, attempt admin-only actions (role changes, user management) directly against the API, bypassing the frontend.
Authentication abuse — brute-force / repeated failed login attempts to confirm rate limiting or lockout behavior triggers.
Token handling — test expired JWT rejection, tampered JWT rejection (altered payload/signature), and behavior after logout/token invalidation where applicable.
Sensitive data exposure — confirm password hashes, tokens, and secrets never appear in API responses or logs.
CORS / origin checks — confirm the API rejects requests from non-allow-listed origins in a production-like configuration.
Findings from these tests (pass/fail, any issues found and fixed) must be written into SECURITY.md as part of the Security Review deliverable.

New — Security Review and Known Limitations deliverables: The assessment brief expects two documentation items beyond a features list, which are added here as required deliverables:
Security Review (in SECURITY.md) — a short self-audit section: what was checked (linking to the Security Testing checklist in Section 20), what was found, and what was fixed or accepted as a residual risk. This is a review artifact, not just a list of implemented features.
Known Limitations (in README.md or a dedicated KNOWN_LIMITATIONS.md) — an explicit list of anything scoped out or simplified for time (e.g. no password reset, single-currency pricing, no payment gateway, simplified low-stock config, etc.), so reviewers know these are deliberate decisions rather than oversights.

8. RBAC Implementation
Backend authorization must not depend only on frontend route protection.
Every protected API must verify:
Authentication.
User role.
Resource ownership where required.
Example:

Staff → GET operational orders
Admin → GET all orders
A customer must not be able to access another customer's order by changing the order ID.

11. Stock Concurrency Strategy
To prevent overselling:
Recheck stock during checkout.
Use database transactions.
Lock product records during critical stock updates where supported.
Reject checkout if available stock is insufficient.
Conceptually:
BEGIN TRANSACTIONLOCK PRODUCTIF stock >= requested_quantity    reduce stock    create orderELSE    reject checkoutCOMMIT
12. Order Status Transition Rules
The API must validate status changes.
Example:
PENDING → CONFIRMED
CONFIRMED → PREPARING
PREPARING → READY_FOR_PICKUP
PREPARING → OUT_FOR_DELIVERY
READY_FOR_PICKUP → COMPLETED
OUT_FOR_DELIVERY → DELIVERED
Invalid example:
PENDING → DELIVERED
This request must be rejected.
13. Pickup Capacity Logic
Available capacity:
available_capacity = slot.capacity - number_of_active_orders
Before order creation:
if active_orders >= slot.capacity:    reject checkout
This validation must occur inside the critical order-processing workflow to reduce overbooking.
14. Return Eligibility Logic
Pseudo-logic:
IF order.status NOT IN [DELIVERED, COMPLETED]:    rejectIF current_date > completion_date + 7 days:    rejectIF order_item already has completed/active return:    rejectELSE:    create request
15. Exchange Validation Logic
Validate original item eligibility    ↓Validate replacement product    ↓Check replacement stock    ↓Create exchange request    ↓Staff/Admin reviews    ↓Approve or reject
Exchange → Order Status Interaction  [ADDED]
The original documents did not specify what happens to order state once an exchange is approved. This must be an explicit decision before implementation; two viable approaches:
Option A — In place: the original OrderItem is updated with the new product and the ReturnExchangeRequest is marked COMPLETED. No new Order is created. Simpler, but the order's item history no longer reflects exactly what was originally delivered.
Option B — Linked record: the original order/order item stays untouched (as a snapshot), and the ReturnExchangeRequest itself carries the replacement product and becomes the source of truth for what the customer ultimately received. No new Order object is created either, but the order history stays accurate.
Recommendation: Option B keeps OrderItem as a true historical snapshot and avoids mutating financial/order records after the fact — but either is acceptable as long as the choice is documented (Section 28) and consistently implemented.

Security Tests  [ADDED]
The assessment brief lists security testing as its own category — the original TRD only covered this implicitly through auth/authorization tests above. Add explicit coverage for:
SQL injection / input sanitization — confirm serializers and ORM usage reject or safely escape malicious input rather than relying on Django's defaults untested.
Broken access control — attempt to access another user's cart, order, or return request by manipulating IDs directly (IDOR-style checks).
Rate limiting / brute-force login — confirm repeated failed logins are throttled and return 429.
JWT tampering and expiry — confirm a tampered, expired, or malformed token is rejected with 401, and that a used refresh token behaves as expected.
Findings from this section feed directly into the SECURITY.md self-audit described in Section 27.
